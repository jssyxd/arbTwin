“深度低估 59 倍”是什么意思，是否该只用 WebSocket 第 3 轮

用户
深度 │ REST 200 档 │ REST 250 档 │ 用 5 档会把 AAPL 1% 深度低估 59 倍（$12.4k vs $736k），是什么意思，我是否放弃REST 而只用Websocket收听
助手

1. 这句话的意思：59 倍来自视野，不是流动性

AAPL-USDT-SWAP：价格 342.275、tickSz = 0.01 → 1 tick = 0.292 bps。所谓"1% 深度"= 以中间价为中心 100 bps 区间内的名义金额，即 343 个 tick 之外。你只取 5 档时，最深的档位离中间价只有 5×0.292 ≈ 1.46 bps。

取数视野（离 mid 最远档）1% 区间内名义（双边）
books?sz=51.5 bps$12.4k
books?sz=20058 bps$736k（仍是下界）
books?sz=400218 / 230 bps$765k / $859k

$736k ÷ $12.4k ≈ 59。不是盘口差了 59 倍的流动性，是采样视野窄了 40 倍。 BTC 更极端：tick = 0.013 bps，400 档也只有 5.3 bps 视野。

2. 要不要弃用 REST、只留 WebSocket？

不要。但两者用途必须分开，混用才是危险。

  • Lighter 的订单簿是稀疏的：AAPL 只有 88 个价位却跨了 4983/20099 bps，NVDA 235 个价位跨 5141/19154 bps → orderBookOrders?limit=250 已完整覆盖 1%，且与 WS 快照深度完全一致（ratio = 1.00）。
  • OKX 的 WS 全量深度确实存在：books 通道实测返回 400/400 档，带 seqId/prevSeqId/checksum，100ms 快照 + 增量。
方案收益代价
WS 全量 books 维护本地簿gate 刷新可到 100ms 级必须做断档检测 + checksum 校验 + 重订阅；漏一次断档就是静默残缺的深度
REST 深档（当前）每次都是完整快照，天然自愈每标的约 1 次调用，TTL 1.5s 复用

分工：定价/成交判定 ← WS top-of-book；深度/操纵成本 ← REST 深档（400/250）。代码里物理隔离：OkxVenue.quote()（WS 5 档）与 OkxVenue.book()（REST 400 档）不共用缓存。

3. 已按这个结论改完并验证

usd, covered_bps, complete = book.depth_covered(100)     # 视野不足返回 complete=False
density = usd / min(100, covered_bps)                    # 与 tick 密度无关
gate:   density >= min_depth_usd_1pct / 100
  • OKX 深度默认 400 档、Lighter 250 单；12 标的单轮 poll 24s → 10–16s（本机走代理）。
  • 顺手修掉一个静默 bug：OKX /market/ticker 不返回 idxPx，原代码把 index 回退成 mark → mark-index 偏离恒为 0。现在 index 取自 /market/index-tickers?quoteCcy=USDT，实测 MSTR：mark 128.51 / index 128.52 / 偏离 0.78 bps。
  • mark/index/OI 改成 3 个全市场批量接口 + single-flight TTL 5s（36 次/轮 → 3 次/轮），资金费 300s TTL。

4. 什么时候才值得上 WS-only 深度

只有当入场门槛压到 < 5bps 且 gate 需要 sub-300ms 刷新 时才值得。当前基差 p95 是 7–13bps、成本 4–10bps，瓶颈在"错价窗口是否出现"，不在"深度数据晚 300ms"。届时必做：seqId 连续性、checksum 校验、断档重订阅、以及每小时用 REST 快照对账一次（top-5 或 1% 深度偏差 > 1% 强制重同步）。
