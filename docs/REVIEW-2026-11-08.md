# 多透镜评审：对 `对话.txt`（另一会话的 basis_cal 分析）与本仓库的校正清单

评审对象：
1. `D:/Users/da/Desktop/对话.txt`（538k 字符）——另一个会话用 `basis_cal` 工具对同一策略做的独立分析，
   结论是 **NOT TRADEABLE**，关键数字：`b* ≈ 7.6 bps` vs RTH 内 `p95|basis| ≈ 1.2 bps`；闭市 p95 是 RTH 的 78×；
   开盘跳空 43.8 bps ≈ 典型步长的 65×；闭市时 Lighter 盘口 `stale = 0.986`（120 秒仅 53 次更新）。
2. 本仓库 `arbTwin`（wave 模式、b* 缺失、anchor 未接线等）。

评审方式：5 个并行透镜（统计方法论 / 策略机制 / 执行与风控 / 数据契约 / 运维与验收）+ 逐条独立复算。
**每条结论都必须能用仓库代码或现场数据复现**，不接受"看起来对"。

## 1. b*（盈亏平衡基差）缺失 —— 选票全部要重排

**证据**：仓库 `screening.py` 原来只做 `basis_p95 − 4bps(手续费) > 0`；`对话.txt` 的核心量是
`b* = 费率 + 半价差 + 逆向选择`，其取值 **7.6 bps**，而 SPY 的 RTH `p95|basis|` 只有 **1.2 bps**。

**复算**（2026-11-08 现场盘口，`b* = 4 + 2×avg(half-spread) + 1`）：

| 标的 | p95 | OKX 价差 | Lighter 价差 | b* | p95 − b* |
|---|---:|---:|---:|---:|---:|
| COIN | 10.39 | 0.7 | 1.1 | **6.8** | **+3.59** |
| VVV | 11.38 | 1.0 | 2.1 | **8.1** | **+3.28** |
| LIT | 11.39 | 0.3 | 1.2 | **6.5** | **+4.89** |
| MSTR | 12.45 | 0.8 | 1.6 | 7.4 | +5.05（11-12 前禁） |
| SNDK | 8.16 | 1.2 | 1.2 | 7.4 | +0.76（too thin） |
| SOXL | 10.79 | 2.2 | 4.3 | **11.5** | **−0.71** |
| GRAM | 15.58 | **9.4** | 1.6 | **16.0** | **−0.42** |
| MRVL | 8.53 | 0.7 | 3.5 | 9.2 | −0.67 |

**结论**：v1 starter 原来的 `SOXL / GRAM / VVV` 里，**SOXL 与 GRAM 在 b* 口径下不成立**（GRAM 的
OKX 价差单独就 9.4 bps）。改为 **COIN / VVV / LIT**，MSTR 作为 11-12 之后的第一候选。

---

## 2. anchor 是死代码 —— 这正是 `对话.txt` 里"有信号时没流动性"的入口

**证据**：`grep -rn "AnchorBook(" arbtwin/` 无结果；`anchor.decide()` 无调用点；
`SymbolState.session` 只被赋值，从未参与判断。

**后果**：`session: us_equity` 对决策零影响。闭市时段引擎照常给股票类永续挂双向单，
而那正是另一会话测到的：Lighter 盘口 `stale 0.986`、120 秒 53 次更新、开盘跳空 43.8 bps
（= 典型步长的 65 倍）。也就是说：**你会挂在一个死盘口里，唯一成交发生在开盘跳空那一刻。**

**修法**：`_gate_symbol` 增加 `st.session.is_open(now)`；闭市时 `allow=False`、只允许减仓，
并把 `session_open` 写进 metrics（监控能看到）。

---

## 3. wave 模式没有持仓记忆 —— 重启即失忆

**证据**：`rounds.jsonl` 只写不读；`wave_step` 从不调用 `venue.positions()`；
`deploy/arbtwin.service` 是 `Restart=always`。

**后果**：进程重启（含 OOM、`systemctl restart`、部署）后，引擎认为 FLAT，会在已有持仓之上
再挂一轮 → 实际仓位翻倍，而 `max_open_symbols` 与单标的限额都拦不住。

**修法**：启动时读一次两所持仓，任何非零仓位登记为 orphan（critical 告警）并**阻断该标的的新开仓**，
直到 `snapshot` 里的持仓归零才解除。

---

## 4–5. 摩擦与参数

* 同一个价位每 5 秒"撤单 + 重挂"一次：没有队列收益，只是浪费 nonce/延迟。现在同价同量直接 hold。
* `WaveParams.min_edge_bps` 0.5 → 2.0：4 bps 手续费 + 2–8 bps 半价差面前，0.5 bps 的"净edge"没有意义。

---

## 6. 成交实现（未修，需要 tick 数据）

复算 14 天小时线：在 p95 事件处，**下一小时仍在 p95 的比例只有 10%–50%**；
而 1 小时的平均回归幅度是 **3.4–9.6 bps**。这说明"在 p95 挂单并按 p95 成交"的假设偏乐观——
真实成交更可能发生在回归途中（对手方主动打穿你），并且有 13%–15% 的单腿成交概率
（`对话.txt` 的 `p_fail`）。建议：给 edge 乘一个 `capture_fraction`（先取 0.5），
或用 `basis_cal record` 那样的 tick 录制实测；不要用小时线自证。

## 7. 每轮流量（未修）

| 项 | 实测 |
|---|---:|
| OKX `books?sz=400` | 20 KiB |
| Lighter `orderBookOrders?limit=250` | 49 KiB |
| 3 标的 / 轮 | 208 KiB |
| 1s 轮询 / 小时 | **767 MB** |
| 每天 | 18.4 GB |

1C/1G 的机器每秒解析 208 KiB JSON 是可行的（CPU ~15%），但没有必要：
深度闸门不需要 1 秒级新鲜度，把深度快照做 2–3 秒 TTL 或每 N 轮取一次即可降 3 倍。

## 8. screening 的成本口径不一致（已修）

第一版 b* 把 8 个标的全部拒绝，原因是 `screening` 里 `maker_fee_bps` 用的是
`round_trip_bps(..., "post_only", "post_only")` 而**没传 `close_type`**，于是平仓按 taker 计 →
7 bps 而不是 4 bps。这与 `spread.py` 里已修过的同类问题一致：成本口径必须只有一个 owner。

## 9. `对话.txt` 的 78× 不能外推（已验证）

用同一批 14 天数据按 session 拆开：CLOSED p95 / RTH p95 = **0.82–1.63×**（COIN 0.99、VVV 1.05、
SOXL 0.82、MSTR 1.63），而不是 78×。差异来自标的（SPY/QQQ 这类极紧的 ETF）与采样频率
（他们 200ms 轮询、闭市几乎无更新 → 表观"基差"其实是 staleness）。所以：

* 他们的 `NOT TRADEABLE` 对 **SPY/QQQ** 是对的；我们的 screen 也早已因成本拒绝 SPY/QQQ/NVDA/AAPL（`maker/maker −2.1 bps` 等）；
* 但**不能**据此判定 SOXL/GRAM 也不成立——要按标的各自算 b*（见第 1 节）。

## 9bis. 对抗式代码评审（ExecutionRisk 透镜）追加的 8 条

| # | 缺陷 | 证据 | 处置 |
|---|---|---|---|
| A1 | **post-only 全挂在可立即成交的价位**（sell=bid、buy=ask）→ live 必被两所拒单，策略从未以 maker 成交 | 原 `wave._entry_orders` / `_requote` | **已修**：拆出 `passive_px()`（卖挂 ask、买挂 bid）与 `marketable_px()`（仅 IOC 用） |
| A2 | live 成交靠盘口穿越"虚构"，无订单状态对账；撤单失败被静默吞掉 | `wavetrader.poll_fills` / `_drop_quotes` | **已修**：`simulate_fills` 仅 dry-run；撤单失败走 `on_error` 告警；**live 启动直接拒绝**（见 A8） |
| A3 | 每 poll 都跑 orphan 对账 → 把自己 wave 的持仓标成 orphan → 该标的永久死锁 | `run_once` 调 `_reconcile_orphans` | **已修**：只在启动时对账；开盘中的 round 永不标 orphan |
| A4 | `ABORT_UNWIND` 的成交被记到 entry_legs，状态机永远回不到 FLAT | `wave.on_fill` 路由条件 | **已修**：路由加入 ABORT_UNWIND，全平即 FLAT（含单测） |
| A5 | 新轮不清 `escalation_used/frozen/round_id` → 第二次需要升级时死挂陈旧价 | `decide` FLAT→ENTRY | **已修**：重置并 `round_id += 1`（含单测） |
| A6 | gate/notional 失败时连持仓的出场与 deadline 都停掉 | `wave_step` 早退 | **已修**：非 FLAT 无论 gate 如何都执行 poll_fills + step |
| A7 | `max_unhedged_notional_usd` 声明但全仓库无执行点；ENTRY_PARTIAL 无逆向止损；forced 平仓用市价 | config / wave / exitqueue | **已修**：裸腿按名义与逆向 bps 双阈值 abort；forced 改为带 collar 的 IOC 限价（操作员"永不市价"）；参数从 limits 注入 |
| A8 | 无成交对账却可 live 启动 | `run_forever` | **已修**：非 dry-run 直接 `RuntimeError`，等订单状态通道落地再开 |

仍未解决（要在同一轮里补）：`client_order_index` 只做了"单调计数"（避免同毫秒撞号），
**没有做"重发复用同一 index"的幂等**；Lighter 的 cancel 用 client index 是否被接受，
官方文档说两者皆可，需实盘小单验证；`rounds.jsonl` 仍未用于恢复。

## 10. 下一步（按价值排序）

1. **round 恢复语义**：现在只是"阻断"，更合理是"接管"——从交易所持仓反推 round（方向、数量、均价），
   恢复成 `HEDGED` 后只走向 `EXIT_*`。
2. **tick 级 record**（照 `对话.txt` 的工具）：把 `p_fail`、markout、`capture_fraction` 实测出来，
   用来替换第 6 节的假设。
3. **深度快照降频**（2–3 s TTL），把每轮 208 KiB 降到 ~70 KiB。
4. **entry 死线经济学**：90 分钟的 `entry_deadline_s` 是否过长（资金占用 vs 成交概率），需要按标的实测。

## 11. 附录：对 Cbb0fe（HIP-3 ↔ IBKR 股票永续基差）的三方核验（2026-11-09）

来源：`x.com/Cbb0fe/article/2095250548744405297`（2026-09-02 本人长文），moomoo/BlockBeats 中译，
TechFlow / hyperindex 镜像；三份子 agent 分别核身份、核文章、核机制。

### 11.1 已核验的事实（与我们的口径直接相关）

| 事实 | 状态 | 对我们的意义 |
|---|---|---|
| HL 资金费：**每小时**结算，`F = premium_avg + clamp(0.01%-P, ±0.05%)`，**0.5%/h 封顶**，且 **notional 用 oracle 价而非 mark 价** 折算 | VERIFIED（官方文档） | 我们 `funding_cost_bps` 用 r×notional 是对的；但 HL 腿的 carry 不能用 mark 估 |
| Lighter：`funding_clamp_big=4.0`（=0.5%/h）、`funding_clamp_small=0.05%`，与 HL 的钳位**完全同构**；且 `open_interest_limit` 逐市场公开 | VERIFIED（venue API） | `oi_utilization` 不必猜，`orderBookDetails.open_interest_limit` 直接可算（我们目前只在启动时读一次） |
| **HL 的 oracle = 验证者提交的 CEX 加权中位数，OKX 权重 2/13；HL 的 mark = 三项中位数，其中一项是 OKX perp mid（权重 2/9）** | VERIFIED（官方文档） | **HL↔OKX 的"基差"有相当部分是在追我们自己的定价** → 这一对不适合当独立基差来源 |
| HIP-3 由 deployer 自定义 oracle / 资金费钳位 / 可 `haltTrading` | VERIFIED（HIP-3 规范） | 把 `xyz` 当腿必须过 `issuer_risk`（发行方即交易对手） |
| 用户文章的所有 PnL / 量 / 事故金额 | 作者自报，**未审计**；且"1.5% of TradeXYZ volume"与公开总量口径不符（按公开量算 2.5–6%） | 只能当机制与参数结构的参考，不能当业绩基准 |

### 11.2 由此改变的两个判断

1. **不做「OKX ↔ HIP-3 xyz」这条腿**（推翻本文 1.4 的候选）。原因：HL 的 oracle/mark 都含 OKX 输入，
   两腿共源 → 测出来的基差是"设计使然的收敛"，不是两套独立订单流的错配；`anchor.py` 的
   `index_agreement_bps` 想防的正是这件事。
2. **OKX ↔ Lighter 是当前唯一"两边 oracle 独立"的组合**（Lighter 的 `index_price` 来自其自身参考源），
   所以之前所有 b\* 与 p95 结论继续有效。

### 11.3 已落地：对冲连续失败熔断（来自 $1.1M 事故）

`main` 新增 `limits.max_hedge_failures=3` / `hedge_failure_cooldown_s=300`：
同一标的对冲连续失败 3 次 → 该标的进 `benched`，`wave_step` 拒绝新报价并 critical 告警；
一次成功对冲清零计数。测试 `test_hedge_failures_bench_the_symbol`。

仍未落地（已定义、待实现）：**持仓读数时效戳**——`reconcile.py` 现在比较持仓差，但没有记录
"这次读数是多久之前的"。CBB 的事故根因正是"拿到一份没刷新的持仓数据后继续加仓"，判据应为
"同一标的处于 ENTRY_PARTIAL 超过 N 秒且该 venue 持仓读数无变化 → critical"。
